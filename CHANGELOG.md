# Changelog

steelix (the CLI, on PyPI) and `steelix-runtime` (the crate generated code depends on, on crates.io) are released together. Generated crates depend on the runtime by its first two version numbers (`steelix-runtime = "0.3"`), so a crate generated by steelix 0.3.x builds with any runtime 0.3.x, and a crate generated by an older minor version keeps building against the runtime it was generated for. A new minor version of the runtime is not compatible with code generated by an older steelix: regenerate the crate, or port its rewritten functions by hand (the incompatible changes are listed below).

## 0.3.3 (2026-11-23)

The runtime only gained a new public item, so crates generated by 0.3.0 to 0.3.2 keep building with runtime 0.3.3; code generated by 0.3.3 needs runtime 0.3.3 for `rt::checkpoint`.

- Native loops no longer starve other threads: `while` loops call `rt::checkpoint(py)?` (instead of `py.check_signals()?`) and `rt::iter` does the same, which hands over the GIL when another thread asked for it and runs pending signal handlers. Recursive calls and resumed generators hand over the GIL as well. Replace `py.check_signals()?` in rewritten loops with `rt::checkpoint(py)?`.
- `steelix transpile` and `steelix build` refuse to overwrite files of the output crate that were changed after steelix wrote them (`--overwrite` replaces them). What was generated is recorded in `.steelix-generated` in the crate.
- The generated `build.rs` refers to the Python project by a path relative to the crate, so a crate that moves together with the project keeps building.
- An unread `_` in an unpacking is written as `_` instead of a binding named `underscore`.

## 0.3.2 (2026-11-11)

Generated code is shorter. The runtime only gained new public items, so crates generated by 0.3.0 and 0.3.1 keep building with runtime 0.3.2; code generated by 0.3.2 needs runtime 0.3.2.

- Common builtins called with positional arguments are written as `rt::builtins::int(py, (&x,))?` instead of `rt::builtin(py, "int")?.call1((&x,))?`.
- Function locals that can only hold a list, dict or set literal or comprehension get the concrete type (`let xs = PyList::empty(py);`), so `xs.append(&x)?` and `len(xs)` need no dynamic calls.
- Functions that never return a value return `PyResult<()>` and end in `Ok(())`.
- Fixed: `{1} in s` on a set local raised `TypeError`; `str(x) == x` did not compile.
- Runtime: new `rt::builtins::*`, `rt::Jump` and `rt::function::IntoReturn`.

## 0.3.1 (2026-11-10)

- Generated crates build and run on macOS and Windows (on the machine they were built on). `steelix build` (relocatable distributions) remains Linux only and reports an error on Windows.
- `steelix test` works on Windows (the interpreter link is a hard link or copy).
- Runtime: links the interpreter's import library on Windows. No change to the public interface.

## 0.3.0 (2026-11-10)

Incompatible runtime changes (`steelix-runtime` 0.3, new dependency `steelix-runtime-macros`):

- The `rt::frame!(m, "f", N, |frame| { .. })` closure is replaced by an attribute on the function, `#[rt::frame(m, "f", N)]`; a body that uses the frame names it as a fourth argument (`#[rt::frame(m, "f", N, frame)]`), and recursive functions add `recursive` instead of creating an `rt::RecursionGuard` themselves.
- `frame.matches(&err, N, || ..)` loses its line argument: `frame.matches(&err, || ..)`, or `frame.matches_at(&err, N, || ..)` with `--traceback-lines`.
- Nested functions, lambdas and generator expressions take their qualname from the frame (`rt::function!(frame, inner(..))`) instead of an explicit `qualname = "..."`.

This version was published on crates.io only, not on PyPI.

## 0.2.0 (2026-11-04)

- Coroutines (`async def`, `await`, `async with`, `async for`) and generator functions are transpiled to native code instead of being kept as Python.
- `match` statements are transpiled to native code (except OR patterns with captures).
- New command `steelix test CRATE -- ARGS` runs the project's pytest suite with the generated program as the interpreter.
- New command `steelix attrs`: which functions read and write the attributes of a class, and `--pyclass NAME` for a `#[pyclass]` draft.
- Methods and decorators are written inside `rt::def!` the way they appear in the Python source.
- Modules of namespace packages are transpiled.
- Release builds use LTO; calls that fill in defaults or pass keywords are faster.

Incompatible runtime changes (`steelix-runtime` 0.2): new coroutine and `match` support (`rt::Coroutine`, `rt::await_`, `rt::delegate`, `rt::match_seq` and others), `rt::Frame` has a second lifetime (`Frame<'a, 'py>`), `except` blocks bind the exception with `let e = frame.catch(err);` returning an `rt::Caught`, and `for` loops iterate with `rt::iter(&xs)?`, which also checks for signals.

## 0.1.0 (2026-11-03)

First release: `steelix transpile`, `steelix build` (relocatable distributions on Linux) and `steelix coverage`; executables (`--mode bin`) and extension modules (`--mode ext`); multi-module projects and `-m`; mixed mode, where unsupported statements are kept as Python; `--traceback-lines`.
